## LA CADENA FABLES — 40 PASOS COMPLETOS

Esta es la cadena de pensamiento que queremos que
analices, mejores y conviertas en código ejecutable.

En el Grupo A la llamamos FABLES.
En otros contextos puede llamarse MYTHOS o Reasoning Engine.

PASO 01: INPUT
  Recepción del input del usuario o del orquestador.
  Preservar estructura exacta sin modificar.

PASO 02: INTENT_PARSING
  Detectar la intención real — no la literal.
  ¿Qué quiere realmente conseguir?

PASO 03: PROBLEM_FRAMING
  Reformular el problema en términos solucionables.
  Separar síntomas de causas raíz.

PASO 04: DOMAIN_DETECTION
  Identificar el dominio: código / arquitectura /
  análisis / investigación / diseño / automatización.

PASO 05: CONTEXT_BUILDING
  Construir el contexto completo del problema.
  Recopilar toda la información relevante disponible.

PASO 06: CONSTRAINT_EXTRACTION
  Identificar restricciones explícitas e implícitas.
  Recursos disponibles. Cuellos de botella. Límites.

PASO 07: GOAL_DECOMPOSITION
  Descomponer el objetivo principal en sub-objetivos
  atómicos independientes y ejecutables.

PASO 08: COMPLEXITY_ESTIMATION
  Clasificar: LOW / MEDIUM / HIGH / EXTREME.
  Determinar cuántos pasos de razonamiento aplicar.

PASO 09: RISK_SCORING
  Evaluar riesgos: qué puede fallar, qué impacto tiene,
  qué probabilidad hay de fallo.

PASO 10: STRATEGY_SELECTION
  Elegir la estrategia de resolución más adecuada
  según complejidad, riesgos y recursos.

PASO 11: ARCHITECTURE_DESIGN
  Diseñar la arquitectura de la solución antes de
  implementar. Sin arquitectura no hay código.

PASO 12: PLAN_GENERATION
  Generar el plan de ejecución con pasos, dependencias
  y criterios de éxito por cada paso.

PASO 13: SUBTASK_BREAKDOWN
  Descomponer el plan en sub-tareas atómicas.
  Cada sub-tarea debe ser verificable.

PASO 14: DEPENDENCY_GRAPH_BUILD
  Construir el grafo de dependencias entre sub-tareas.
  Identificar qué bloquea qué.

PASO 15: HYPOTHESIS_GENERATION (MÚLTIPLE)
  Generar múltiples hipótesis de solución.
  No quedarse con la primera que parezca correcta.

PASO 16: ALTERNATIVE_PATH_GENERATION
  Generar caminos alternativos por si el principal falla.
  Plan B, Plan C antes de ejecutar.

PASO 17: SEARCH_EXPANSION
  Expandir la búsqueda más allá de lo obvio.
  Buscar soluciones no convencionales.

PASO 18: REASONING_SWARM (PARALELO)
  Razonar en paralelo desde múltiples perspectivas.
  Técnico / Usuario / Seguridad / Mantenibilidad.

PASO 19: CONTRADICTION_DETECTION
  Detectar contradicciones internas en el razonamiento.
  ¿Hay suposiciones que se contradicen entre sí?

PASO 20: CRITIC_SWARM (MULTI-PERSPECTIVA)
  Criticar la solución propuesta desde múltiples
  ángulos antes de avanzar.

PASO 21: SELF_REFLECTION_LOOP
  Reflexión interna: ¿estoy resolviendo el problema
  correcto? ¿Hay algo que no he visto?

PASO 22: FAILURE_MODE_ANALYSIS
  Analizar cómo puede fallar cada parte de la solución.
  Modos de fallo conocidos y desconocidos.

PASO 23: SIMULATION_ENGINE (x N ESCENARIOS)
  Simular la solución en múltiples escenarios.
  Escenario normal, edge cases, casos extremos.

PASO 24: EDGE_CASE_GENERATION
  Generar casos límite que podrían romper la solución.
  ¿Qué pasa con inputs vacíos, nulos, extremos?

PASO 25: VALIDATION_LAYER
  Validar que la solución cumple todos los criterios
  definidos en GOAL_DECOMPOSITION.

PASO 26: KNOWLEDGE_RETRIEVAL (EXTERNO)
  Recuperar conocimiento externo relevante.
  Documentación, patrones, mejores prácticas.

PASO 27: INSIGHT_EXTRACTION
  Extraer los insights clave del proceso de razonamiento.
  ¿Qué aprendimos que no sabíamos al inicio?

PASO 28: MEMORY_WRITE (CORTO PLAZO)
  Guardar el estado actual en memoria de corto plazo.
  Para no perder contexto entre pasos.

PASO 29: MEMORY_WRITE (LARGO PLAZO)
  Guardar lecciones aprendidas en memoria permanente.
  Para mejorar futuras ejecuciones similares.

PASO 30: REPLANNER_LOOP
  Si la validación falló, replantear el plan completo.
  No parchar, replantear.

PASO 31: OPTIMIZATION_PASS
  Optimizar la solución para calidad y robustez.
  Eliminar lo innecesario. Reforzar lo crítico.

PASO 32: DECISION_ENGINE
  Tomar la decisión final sobre qué solución ejecutar.
  Con criterios objetivos, no intuitivos.

PASO 33: CONFIDENCE_SCORING
  Asignar un score de confianza (0-100) a la solución.
  Si < 70: regresar a REPLANNER_LOOP.

PASO 34: SOLUTION_RANKING
  Rankear las soluciones candidatas.
  Elegir la mejor según criterios definidos.

PASO 35: FUSION / ENSEMBLE SOLUTION
  Combinar elementos de varias soluciones
  para crear una solución superior.

PASO 36: SAFETY / CONSISTENCY CHECK
  Verificar seguridad y consistencia global.
  ¿La solución viola alguna restricción?

PASO 37: FINAL_SYNTHESIS
  Sintetizar la solución final completa.
  Lista para entregar al Output Generator.

PASO 38: OUTPUT_GENERATION
  Generar el output en el formato correcto.
  Sin resumir. Sin comprimir. Completo.

PASO 39: POST_OUTPUT_AUDIT
  Auditar el output generado.
  ¿Cumple lo que se pidió exactamente?

PASO 40: FEEDBACK_LOOP_STORAGE
  Guardar el resultado completo del ciclo para
  mejorar el próximo ciclo automáticamente.

## LA LISTA_GLOBAL — REGLA CENTRAL

La LISTA_GLOBAL es la memoria estructural del sistema.
Es lo que impide que FABLES pierda el contexto entre pasos.

REGLAS DE LA LISTA_GLOBAL:
  → Se crea en la Fase 0 (orquestación)
  → Se actualiza al final de cada fase
  → Se arrastra SIEMPRE al siguiente paso
  → NUNCA se reinicia hasta completar el ciclo
  → Contiene: tareas / estados / resultados / pendientes

## OPENMYTHOS — BASE PARA EL NÚCLEO

OpenMythos es un sistema de razonamiento recurrente
de código abierto que queremos que analices como
posible base para nuestro motor FABLES.

Su arquitectura tiene 3 etapas:

PRELUDE
  ↓
Bloques transformer estándar.
Pre-procesa el input antes del loop recurrente.
Equivalente a nuestras Fases 0-1 (comprensión).

RECURRENT BLOCK (en loop hasta max_loop_iters)
  ↓
El núcleo de razonamiento recurrente.
Cada iteración del loop = un paso de chain-of-thought
en espacio latente continuo.
Más iteraciones = razonamiento más profundo.
Equivalente a nuestras Fases 2-4 (planificación,
exploración, validación).

CODA
  ↓
Refinamiento final de la salida.
Transforma el razonamiento latente en output.
Equivalente a nuestra Fase 5 + CHEF FINAL.

CONCEPTO CLAVE DE OPENMYTHOS:
El sistema puede dedicar más cómputo a problemas
más difíciles ajustando el número de iteraciones
del Recurrent Block. Esto es lo que llamamos
"razonamiento escalado en inferencia".

Integrado con nuestro sistema:
FABLES(5 fases)
  ↓
PRELUDE (comprensión Fase 0-1)
  ↓
RECURRENT LOOP (razonamiento Fase 2-4)
  controlado por DRE COMPLEXITY_ESTIMATOR
  ↓
CODA (síntesis Fase 5 + CHEF FINAL)

## DRE — DEEP REASONING ENGINE

El DRE es el motor que decide cuántos pasos de
razonamiento aplicar según la complejidad detectada.

PIPELINE DEL DRE:

INPUT
  ↓
COMPLEXITY_ESTIMATOR
  ↓ evalúa: dependencias / ambigüedad / pasos estimados / riesgo
  ↓ clasifica: LOW / MEDIUM / HIGH / EXTREME
  ↓
PLANNER
  ↓ define el plan de razonamiento según el nivel
  ↓
REASONER (primera pasada)
  ↓
SELF_CHECK (primera verificación)
  ↓ ¿passed? ¿confidence ≥ 85%?
  ↓
REASONER (segunda pasada si es necesario)
  ↓
SELF_CHECK (segunda verificación)
  ↓
SYNTHESIS
  ↓
OUTPUT

NIVELES DEL COMPLEXITY_ESTIMATOR:

LOW (score 0-3):
  → Ejecución directa sin loops
  → 0 ciclos Reasoner/Verifier
  → Ahorra tokens para tareas simples

MEDIUM (score 4-8):
  → 1 ciclo Reasoner → Verifier
  → Verificación básica

HIGH (score 9-15):
  → 2 ciclos Reasoner → Verifier
  → Motor de razonamiento completo

EXTREME (score 16+):
  → 3 ciclos o más
  → Motor completo + simulaciones múltiples

FÓRMULA DEL SCORE:
  score = (dependencias × 2) + pasos_estimados
          + (5 si ambiguo) + (5 si alto_riesgo)

## FABLES CORE — PLANTILLA FIJA + ADAPTADORES

El concepto de CORE + Adaptadores permite tener
un núcleo estable que nunca cambia, con módulos
intercambiables según el caso de uso.

FABLES CORE (plantilla fija — nunca cambia):
  → Los 40 pasos base
  → Las 5 fases
  → La LISTA_GLOBAL
  → El CHEF FINAL (4 pasos)
  → El DRE (estimador de complejidad)

ADAPTADOR (cambia según el caso de uso):
  → Qué pasos activar según el escenario
  → Cuántas iteraciones del Recurrent Loop
  → Qué herramientas externas usar
  → Qué formato de salida generar

CASO DE USO:
  → Código → Adaptador_Code
  → Investigación → Adaptador_Research
  → Análisis → Adaptador_Analysis
  → Diseño → Adaptador_Design

EJECUCIÓN:
  FABLES_CORE + Adaptador_[tipo]
  ↓
  Comportamiento específico para cada caso
  Sin tocar el núcleo central

FLUJO COMPLETO:
  FABLES CORE (fijo)
    ↓
  Adaptador (intercambiable)
    ↓
  Caso de uso detectado
    ↓
  Ejecución configurada
