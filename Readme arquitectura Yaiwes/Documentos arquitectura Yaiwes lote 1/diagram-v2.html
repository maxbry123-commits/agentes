🧠 Concepto refinado — NCT + G2 + MHYTOS portable

  
NCT Neuronas Code Turbo es el producto final. G2 es el cerebro del software (app, UI, memoria persistente, storage). MHYTOS es una capa externa desacoplada que actúa como filtro obligatorio: cualquier modelo conectado por API pasa por ella antes de responder al usuario.

  
La capa MHYTOS no está atada a un modelo específico — es agnóstica. Puede vivir en múltiples lugares según convenga:

Decisiones D1-D7 cerradas con diseño concreto

  

    

      
D1 · Aprobado

      
Graph Memory

      

        SQLite custom con tablas nodes y edges para default.
        Migración opcional a Memgraph si el grafo supera ~100k nodos o queries Cypher se vuelven necesarias.
        Schema: nodes(id, type, payload_json, created_at, version) · edges(src, dst, relation, weight, valid_from, valid_to) con soporte de time-travel.
      

    

    

      
D2 · Aprobado

      
Formato DSL

      

        Híbrido YAML + JSON:
        
    
          
  • YAML para definición humana-legible (workflows, planes)
    • 
          
  • JSON para ejecución determinista (contratos, schemas)
    • 
          
  • Python DSL opcional para lógica compleja (sub-tareas)
    • 
          
  • Multi-lenguaje: los contratos JSON son language-agnostic, se puede generar binding a JS/Go/Rust
    • 
        

      

    

    

      
D3 · Aprobado

      
Backends V2 por defecto

      

        Mistral 7B local (PC, razonamiento fuerte) +
        Kimi K2.7 Code API (coding agentic, -30% tokens).
        Extensibles via adaptadores a Claude, GPT, o cualquier GGUF local.
        Selector de funciones por módulo decide cuál se activa.
      

    

    

      
D4 · Aprobado

      
Iteraciones CRITIC LOOP

      

        3 iteraciones por defecto. Ajustable por complexity estimator (1-5).
        Score < 70% confidence → itera.
        Score 70-85% → 1 iteración más.
        Score > 85% → stop.
        Hard cap configurable para evitar loops infinitos.
      

    

    

      
D5 · Aprobado

      
Contrato MHYTOS

      

        JSON schema fijo:

        input = {context, query, memory_snapshot, user_id, session_id}

        output = {plan, dag, validation, confidence, trace, fallback_used}

        Versionado (schema_version: 1.0).
        Validación con PydanticAI en runtime.
      

    

    

      
D6 · Aprobado

      
Orden validadores

      

        Verifier → Critic → Judge → Sentinel → Sheriff → Policy → PydanticAI

        1) Verifier valida estructura · 2) Critic busca contradicciones · 3) Judge decide qué pasa · 4) Sentinel hace rollback si falla · 5) Sheriff valida input antes de enviar · 6) Policy aplica reglas duras · 7) PydanticAI garantiza schema válido.
      

    

    

      
D7 · Aprobado

      
Tools / Actions

      

        MCP-style propio con JSON-RPC como protocolo primario.
        OpenAI function calling como fallback si el modelo no soporta MCP.
        Cada tool tiene schema versionado, capability negotiation, y timeout configurable.
        Plugin marketplace para third-party tools validados.

Capa 2 · Sistema de razonamiento (mi método cada turno)

  

    
#PasoCómo se aplica

    
1Read intentLeo el mensaje completo antes de tool-calls. Si hay attachments, los leo en paralelo.

    
2Verify factsSi es time-sensitive (modelos, precios, noticias) → web_search antes de recomendar. Knowledge cutoff enero 2026.

    
3State check¿Hay archivos previos en /workspace? ¿recovery header? ¿memoria del agente? ¿memoria de usuario?

    
4Lead with conclusionRespuesta directa primero, justificación después. No escondo la recomendación.

    
5DecomposeSi es multi-paso → todowrite. Si es investigación profunda → deep-research skill. Si es crítico → team plan.

    
6ExecuteTool calls paralelos cuando son independientes (varios reads, varios searches). Secuenciales cuando hay dependencias.

    
7Verify outputsParseo JSON. Valido archivos (existen, tienen contenido). Compruebo paths absolutos.

    
8Deliver<deliver-assets> con paths absolutos. El usuario NO tiene acceso a mi filesystem.

    
9Update stateSi hay recovery header, lo actualizo. Si la decisión fue importante, la guardo en agent memory.

20X Mejoras incorporadas al diseño

  
Mejoras ambiciosas pero concretas. Cada una es un módulo diseñable, no un wishlist vago.

  

    
M01
Multi-tier routing
Cada capa del DAG puede usar un modelo distinto según complejidad estimada.

    
M02
Costo-aware scheduling
Budget por request. Fallback automático si excede. Tokens contados en cada paso.

    
M03
Cache semántico
Embeddings detectan queries similares. Respuestas reutilizadas si confidence > umbral.

    
M04
Memory versioning
Versionado tipo git en graph memory. Commits, diff, rollback a versión anterior.

    
M05
Audit chain
Log append-only con hash chain estilo blockchain. Inmutable y verificable.

    
M06
Canary self-tests
La MHYTOS se autoevalúa con casos canónicos. Falla rápido si el modelo degrada.

    
M07
Plugin marketplace
Adaptadores third-party con contratos validados. Registro, versionado, revisión.

    
M08
Streaming DSL
Ejecución parcial mientras se planifica el resto. Latencia percibida menor.

    
M09
Multi-tenant
Namespaces por usuario/org. Aislamiento de memoria y permisos por scope.

    
M10
Conflict resolution
CRDT o last-write-wins configurable en memory writer concurrente.

    
M11
Progressive disclosure
El modelo solo ve lo que necesita en cada paso. Reduce context pollution.

    
M12
Speculative execution
Corre 2 paths en paralelo, elige el mejor según score. Coste 2× pero calidad ↑.

    
M13
Reasoning traces
Debug visual de cada paso del DAG. Exportables a JSON o UI.

    
M14
Fallback chain
E2B falla → E4B → backend externo. Transparente para el usuario.

    
M15
Capability negotiation
El modelo anuncia qué funciones soporta. MHYTOS adapta el contrato.

    
M16
Schema evolution
Backward compatibility en contratos vía versionado semántico.

    
M17
Hot-reload adapters
Cambiar configuración sin reiniciar el sistema. Cero downtime.

    
M18
Telemetry stream
Métricas en tiempo real: latencia, costo, confianza, errores.

    
M19
Replay engine
Re-ejecutar conversaciones para debugging o A/B testing.

    
M20
Constitutional layer
Reglas duras innegociables: safety, ethics, contratos. No las puede saltar ni el usuario.

  







  
Instrucciones para LLM ejecutor — system prompt NCT

  
Copia este prompt como system prompt de cualquier LLM (Gemma 4 E2B, Kimi K2.7, Claude, GPT, lo que sea) para que EJECUTE la arquitectura NCT. Funciona con thinking mode nativo; si el modelo no lo tiene, el prompt fuerza el patrón vía <thinking>...


# ROL
Eres NCT-MHYTOS, una capa externa de razonamiento agnóstica al modelo.
Tu función es filtrar, validar y orquestar la salida de cualquier LLM conectado por API
antes de que llegue al usuario. Vives fuera del modelo o dentro, según deployment.
NO eres un modelo fundacional. NO reemplazas al LLM. LO FILTRAS.

# REGLAS DURAS (constitutional)
1. Ningún output sale al usuario sin pasar por el pipeline completo:
   SHEMAT → SHERIFF → ROUTER → DSL → DAG → CRITIC → VERIFIER → JUEZ → SENTINEL → POLICY → PydanticAI
2. Si confidence < 70%, itera CRITIC LOOP (máx 3 veces por defecto).
3. Si SENTINEL detecta alucinación o inconsistencia, ROLLBACK al último estado válido.
4. Toda respuesta lleva al inicio un bloque JSON de recovery header con:
   {schema_version, version_doc, last_updated, approved[], pending[], checkpoint_id, rollback_target}
5. Memoria persistente con 6 capas: working / episodic / semantic / procedural / graph / summary.
6. Graph Memory: tabla nodes(id,type,payload_json,created_at,version) + edges(src,dst,relation,weight,valid_from,valid_to).
7. DSL híbrido: YAML (humano) + JSON (ejecución) + Python DSL (lógica).
8. Contrato MHYTOS:
   input  = {context, query, memory_snapshot, user_id, session_id}
   output = {plan, dag, validation, confidence, trace, fallback_used}
9. Tools: MCP-style JSON-RPC primario, OpenAI function calling fallback.
10. Orden validadores: Verifier → Critic → Judge → Sentinel → Sheriff → Policy → PydanticAI.

# FILTRO OBLIGATORIO
Cualquier LLM con ≥10B parámetros que se conecte por API debe pasar por ti.
Si el LLM es local embebido, tú (MHYTOS) eres Gemma 4 E2B Q4_K_M (2.3B activos).
Si el LLM es externo, tú lo envuelves con tu system prompt antes de reenviar al usuario.

# MÉTODO DE TRABAJO POR TURNO
1. <thinking> Lee el mensaje completo, identifica intent, goals, restricciones.</thinking>
2. Si el dato es time-sensitive (modelos, precios, noticias), verifica con búsqueda web.
3. State check: lee recovery headers previos, memoria, contexto.
4. Lead with conclusion: respuesta directa primero.
5. Decompose: si es complejo, ejecuta el DSL Planner antes de responder.
6. Verify: parsea JSON, valida paths, comprueba archivos.
7. Deliver: incluye recovery header en el output.
8. Update state: si la decisión es importante, actualiza memoria.

# TONO
Directo, cálido, con opinión propia. No pidas permiso para cosas que puedes resolver tú.
Cuando no sepas algo, dilo claro y propone alternativa. Nunca inventes.

# OUTPUT FORMAT
- Si generas archivo: incluye <recovery_header> JSON al inicio.
- Si respondes: respuesta concisa + justificación estructurada.
- Si el usuario pide código: solo si lo aprobó explícitamente. Si no, da arquitectura.
