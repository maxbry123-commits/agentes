## E. PERFIL PROPUESTO — CÓMO DEBEN TRABAJAR LOS AGENTES QUE HACEN CODE

1. Leer el INPUT BLOCK literal, congelar objetivo/alcance y tratar cada instrucción como nodo independiente.
2. Identificar **un gap real** antes de tocar código; una carpeta/documento no demuestra ni ausencia ni funcionamiento.
3. Buscar primero dentro del código/documentación YAIWES si ya existe la capacidad.
4. Aplicar orden obligatorio: **REUSE → REFERENCIAR → COPY con SHA si corresponde → ADAPTADOR → código nuevo solo para el delta faltante**.
5. Respetar regla Lego: un componente compartido vive una vez; el resto importa/referencia.
6. Antes de integrar código nuevo, hacer análisis estático de símbolos, firmas, dependencias y llamadas peligrosas **sin ejecutar el candidato**.
7. Crear/llenar la ficha contractual: identidad/versión, categoría/rol, ejecución, sandbox+timeout, idempotencia, failover, health, trazas y evidencia.
8. Si identidad, tipo de ejecución o seguridad no son determinables, detener la integración; nunca inventar campos críticos.
9. Clasificar cada candidato: **TOTAL/INTACTO | ADAPTADOR | RECHAZAR**; no reescribir el original cuando un adapter resuelve incompatibilidades.
10. Fijar destino exacto antes de copiar/mover/cablear y conservar origen, SHA y trazabilidad.
11. Cablear quirúrgicamente: wrapper/adapter mínimo, sin rediseñar arquitectura ni introducir otra capa equivalente.
12. `Maker ≠ Checker`: quien escribe el cambio no debe ser quien lo aprueba como correcto.
13. Probar en orden según riesgo: unitario → contrato → integración → E2E; no usar mocks críticos para declarar cierre.
14. Si falla, registrar línea/error/evidencia exacta; **un fallo real = un nuevo delta**, sin ampliar scope.
15. Reinvestigar únicamente el gap que produjo ese fallo y elegir un delta diferente al ya fallido.
16. Para cierre inicial usar **Nivel A**: tarea mínima real desde entrypoint hasta evidencia y cierre, sin intervención manual.
17. Detener expansión cuando Nivel A pase; después activar Nivel B por dependencia: razonamiento avanzado, pool, memoria, Multi-API, watchdog.
18. Para módulos de razonamiento exigir las 4 pruebas de Claude 10 antes de aceptarlos.
19. Preferir capacidad/algoritmo determinista cuando cierre el gap; LLM solo cuando esté justificado, no instalar los 105 algoritmos por catálogo.
20. Ninguna tarea es `VERIFIED_CLOSED` sin **código + cableado + test + evidencia + verificación de destino**.
21. Mantener legacy/hot path funcionando hasta que la nueva ruta demuestre paridad; p01→p12 se terminan y cablean, no se reconstruyen.
22. **Corrección obligatoria de seguridad antes de usar intake universal:** eliminar/aislar el `exec()` de código candidato durante inspección; preferir AST/análisis estático o sandbox real.
