1. LOS 10 ROLES DE GOBIERNO (el "sello" que lleva cada micro-proceso)

No son solo del documento completo — se aplican a CADA micro-proceso dentro de cada fase, como un sello que muestra cuáles están activos para ese paso específico:

DSLDAG SchemaSheriff SentinelaJuez SupervisorValidador VerificadorOrquestador

Verde = activo para este proceso · Azul = pendiente de activar · (ejemplo ilustrativo del sello, no de una fase real)

2. LAS 9 CARACTERÍSTICAS QUE EL DOCUMENTO DEBE CUMPLIR (literales)

  1. Es un prompt viviente — no una explicación sobre el sistema, sino algo que al leerse FUNCIONA como instrucción ejecutable
  2. Cada fase: 3 a 100 tareas — nunca menos de 3, nunca más de 100
  3. Declara qué DEBE y qué NO DEBE ejecutar el software en cada fase, sin ambigüedad
  4. Raíz estructural extendida — fuente exacta + conexión con el proceso anterior Y con el siguiente, en cadena
  5. Se lee sin necesidad de interpretar — cualquier IA o persona entiende el sistema completo solo leyendo
  6. Es un borrador vivo — se actualiza según se cierran partes, nunca es un documento "terminado y quieto"
  7. Se divide en documentos de poca información — nunca un solo documento gigante; varios documentos pequeños que, juntos, forman el sistema completo
  8. Permite auditar Y reemplazar partes del sistema, no solo revisar
  9. Es la radiografía de un proyecto maestro moderno — desde ahí se genera, en cadena, el código real → UOOS Parte 1 → Parte 2 → despliegue
Corrección sobre la v1 de este documento: esta misma especificación es una guía única (correcto, porque es el MANUAL), pero el PIPELINE en sí, cuando se construya, debe salir en VARIOS documentos pequeños — nunca uno solo gigante. Ver sección 6.

3. EL ÍNDICE MAESTRO DE AUDITORÍA (paso previo obligatorio)

Antes de escribir cualquier fase: lista completa de todos los documentos disponibles (bandeja + chat), cada uno con ruta exacta, resumen de una línea, y si fue leído de verdad o solo referenciado.

Código
ruta_exacta/archivo.py
  contenido: que trae por dentro, en una frase
  verificado: SI (leido) | NO (solo referenciado)
  usado_en_fase: 05, 06

6. CÓMO SE DIVIDE (varios documentos pequeños, nunca uno gigante)

El PIPELINE final NO sale en un solo archivo. Sale en muchos documentos cortos, uno por tramo de fases, para no perder detalle sintetizando. Ejemplo de división:

DocumentoContiene
PIPELINE_00.mdFase 00 completa (núcleo/gobernanza)
PIPELINE_01_02.mdFases 01-02 (idea + requisitos)
PIPELINE_03.mdFase 03 (arquitectura)
… uno o dos por documento, según su tamaño real—

Cada documento pequeño tiene su propia trazabilidad; juntos, forman el PIPELINE completo del proyecto.

7. DEL PIPELINE A UOOS PARTE 1, PARTE 2 Y DESPLIEGUE

Código
cada FASE del PIPELINE → se vuelve un NODO de UOOS Parte 1
raíz estructural extendida → contrato input/output del nodo
sello de gobierno de 10 roles → validaciones del nodo en el DAG
cierre de todas las fases → UOOS Parte 2 (ejecución)
                          → despliegue determinista (0% agente,
                            solo script — ver especificación previa
                            de despliegue ya aprobada)

8. CHECKLIST FINAL

  • Los 10 roles de gobierno considerados (no 9, no menos)
  • Cada fase entre 3 y 100 tareas
  • DEBE / NO DEBE explícito
  • Raíz estructural EXTENDIDA (anterior + siguiente en cadena)
  • Sello de gobierno visible en cada micro-proceso
  • Documento pequeño — nunca un solo archivo gigante para todo el PIPELINE
  • Explicación técnica + simple, mismo contenido
  • Fuentes marcadas verificado ✓ o pendiente
  • Cero alegorías — solo lenguaje de programación real
  • Paleta y tipografía exactas, sin agregados
