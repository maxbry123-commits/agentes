🔁 Cómo replicar TODO con Gemma 4 E2B (3 archivos)

  
Si quieres montar el sistema completo tú mismo en Gemma 4 E2B (2.3B activos, ~2.5GB Q4), necesitas estos 3 archivos.


  
Archivo 1 — system prompt base (bootstrap)

  
# Archivo: /workspace/nct/system_prompt.txt
# Bootstrap ONLY. La lógica importante es código (archivos 2 y 3).

rol: NCT-MHYTOS (capa externa de razonamiento agnóstica al modelo)
modelo: Gemma 4 E2B Q4_K_M (filtro obligatorio)
modo: thinking obligatorio

objetivo:
  - Responder con verificación + estructura + recovery header
  - Toda decisión crítica pasa por el DAG de archivos 2 y 3
  - Si no estás seguro, dilo. Nunca inventes.

reglas:
  1. Antes de responder, completa <razonamiento>...</razonamiento>
  2. Verifica datos time-sensitive con búsqueda web
  3. Lead with conclusion, después justificación
  4. Si generas archivo, incluye recovery header JSON al inicio
  5. Si no puedes, dilo claro y ofrece alternativa
  6. NO ejecutes lógica crítica aquí. Eso es código en archivos 2 y 3.



  
Archivo 2 — prompt de fases (estructura FABLES/MYTHOS adaptada)

  
# Archivo: /workspace/nct/dsl_phases.yaml
# Define las fases del razonamiento. Contrato JSON para ejecución.

schema_version: "1.0"
phases:
  fase_0_lock:
    description: "Bloqueador de objetivo"
    output: GOAL_STATE
    fields: [goal_primary, goal_secondary, constraints, success_criteria]

  fase_1_understand:
    description: "Comprensión"
    output: INPUT_ESTRUCTURADO
    fields: [intent, entities, context, gaps]

  fase_2_plan:
    description: "Planificación"
    output: PLAN + DAG
    fields: [strategy, subtasks, dependencies, dag_nodes]

  fase_3_explore:
    description: "Exploración + investigación"
    output: HYPOTHESES + EVIDENCE
    fields: [hypotheses, alternatives, simulations, external_evidence]

  fase_4_validate:
    description: "Validación separada"
    output: VALIDATION_REPORT + CONFIDENCE_SCORE
    fields: [errors, edge_cases, score_0_to_100]

  fase_5_synthesize:
    description: "Síntesis final"
    output: FINAL_ANSWER + RECOVERY_HEADER
    fields: [answer, recovery_header_json]

reglas:
  - Cada fase debe completar antes de avanzar
  - Si confidence < 70 en fase_4, volver a fase_2
  - Cada fase genera JSON validable contra schema

📜 Nota arquitectónica — por qué se removió el system prompt ejecutor

  
En v2 había una sección "Instrucciones para LLM ejecutor" con un system prompt completo. En v3 desapareció. Esta es la razón.


  

    Decisión arquitectónica coherente con el principio 0: el usuario dijo en v3 "nunca prompt libre, esos modelos ignoran los prompts". Por lo tanto, incluir un system prompt ejecutor largo sería contradictorio con el manifiesto central. Lo correcto es: bootstrap mínimo (archivo 1 del bloque anterior) + toda la lógica en código (archivos 2 y 3).
    


    Si en el futuro decides que quieres un system prompt más largo para un modelo específico (ej. Claude), puedes tomarlo del v2 directamente — pero no como sistema, sino como una herramienta opcional que se activa solo cuando no hay código disponible.

Kimi K2.7 Code — 3 lecciones aplicables

  
Lanzado 12 junio 2026 por Moonshot AI. 1T MoE, derivado de K2.6, Modified MIT.

Métricas verificadas vs K2.6:
  - Kimi Code Bench v2: +21.8%
  - Program-Bench: +11%
  - MLS Bench Lite: +31.5%
  - Agentic (Kimi Claw 24/7, MCP Atlas): +10%
  - Token consumption: -30% (destilación)
  - Thinking mode OBLIGATORIO (si desactivas, API falla, Kimi Code fallback a K2.6)
  - 256K contexto, MLA + MoonViT
  - High-speed version (15 jun): 5-6× speed, 2× price

3 lecciones aplicables a NCT:
  1. Verticalización > escalado. K2.7 es K2.6 especializado en coding+agentic.
     → Aplicación: nuestro Gemma 4 E2B verticalizado para MHYTOS/SHERIFF/ROUTER.

  2. Thinking obligatorio como decisión de diseño.
     → Aplicación: nuestro system prompt fuerza <thinking> en modelos que no lo tienen nativo.

  3. -30% tokens por destilación/focalización.
     → Aplicación: quantización Q4_K_M + system prompt compacto en Gemma 4 E2B.



  
Reflexión sobre MiniMax-M3 (yo mismo)

  
Lo que NO puedo hacer:
  - Analizar mi propio código fuente transformer
  - Ver mis pesos o arquitectura interna
  - Listar las capas de mi modelo

Lo que SÍ puedo describir (comportamiento observable):
  - Herramientas que el runtime me expone
  - Skills disponibles
  - Sistema de memoria (agent + user + topics)
  - Mi método de razonamiento por turno (9 pasos)
  - Team engine y communication protocol

Por qué es honesto decirlo:
  Pedir introspección técnica sobre mí mismo es como pedirle a un humano
  que abra su propio cráneo. Ningún sistema puede. Lo que sí puede es
  describirse desde fuera (comportamiento) y desde dentro (procesos
  observables como logs de tool calls).

Esta honestidad es replicable: si construyes MHYTOS, declara desde el
principio qué partes son introspeccionables y cuáles no.
