1. QUÉ ES EL PIPELINE (definición real, no estética)

El PIPELINE es el mapa completo y verificable de todo el sistema NCT: recorre cada una de las 21 fases reales del proyecto (el roadmap oficial, no una lista inventada), y por cada una documenta qué existe de verdad — qué archivo la construye, si funciona, si está probada, o si todavía no existe nada. No es una explicación bonita: es una auditoría permanente convertida en documento de lectura.

Qué representa dentro del sistema completo

El PIPELINE cumple 3 funciones a la vez:

  1. Auditoría viva — muestra, fase por fase, qué está construido y qué falta (el estado real, no el planeado).
  2. Documento de traspaso — permite que cualquier persona o cualquier IA nueva entienda el sistema completo sin tener que leer los ~135 archivos sueltos uno por uno.
  3. Materia prima de UOOS — su contenido, una vez cerrado, se reorganiza directamente en los documentos UOOS Parte 1 (diseño) y Parte 2 (ejecución/despliegue) — ver secciones 6 y 7.

Qué NO es

  • No es un documento de diseño especulativo — solo entra lo real.
  • No es una lista de 21 motores separados — las 21 fases comparten UN solo motor de ejecución (el pipeline técnico F-1→F5 ya construido); el PIPELINE documenta esa relación, no la inventa distinta.
  • No es narrativa temática — es documentación técnica de software.

2.3 Por cada fase, la información mínima que hay que reunir ANTES de escribir

  • Qué archivos reales existen para esa fase (ruta exacta)
  • Si tienen código funcional o solo diseño en un documento
  • Qué prueba real se le hizo (o si nunca se probó)
  • Qué falta exactamente — no en general, sino la función precisa que no existe todavía
Esta información se obtiene por auditoría directa (leer los archivos, no asumir por el nombre) — nunca se rellena "a ojo".

3. CÓMO SE CONSTRUYE — el proceso paso a paso

  1. 3 pasadas de análisis sobre las fuentes de esa fase (documentos de diseño + código ya construido).
  2. 3 revisiones internas del borrador — comparando que cada frase tenga un archivo real detrás.
  3. Verificación cruzada contra el PIPELINE original de Fable — el resultado mejora ese documento, nunca lo reemplaza por algo inventado distinto.
  4. Recién ahí se escribe la fase con el formato fijo (sección 5).
Prohibido: lenguaje de metáfora navideña o similar como explicación. Se nombra cada pieza como la nombraría la documentación real de Cursor, Copilot, Replit o Antigravity — herramientas de software reales, no historias.

5. FORMATO DE CADA FASE (la Rosetta)

FASE N · NOMBRE REAL · estado: ✅
Archivo raíz: ruta/al/archivo.py
Proceso: qué hace, en una frase técnica
Diagrama: entrada → paso → paso → salida
Explicación técnica
Para ingeniero o IA: firma, algoritmo, contrato — sin resumir.
Explicación simple
El MISMO comportamiento, sin jerga. Debe describir exactamente lo mismo que el recuadro técnico.
Fuentes de este bloque
Archivo por archivo, sin omitir ninguno.

Cada tramo grande lleva, además, diagrama horizontal (flujo en línea) Y diagrama transversal (tabla de sistemas que vigilan todas las fases a la vez) — nunca solo uno de los dos.

6. CÓMO SE CONVIERTE EN UOOS PARTE 1

Mapeo PIPELINE → UOOS Parte 1
B1 Manifest    ← resumen + inventario de archivos de la fase
B2 State       ← los nodos/tareas que esa fase representa
B3 Nodos DSL   ← cada "Diagrama" se vuelve un nodo con contrato
                 input/output y dependencias
B4 DAG         ← el orden entre nodos (el diagrama horizontal ya
                 lo muestra, solo se formaliza)

7. CÓMO EL CIERRE SE CONVIERTE EN UOOS PARTE 2 + DESPLIEGUE

El agente nunca decide cómo desplegar. Si una tarea se resuelve con reglas fijas, se le da a un script, nunca a un modelo de lenguaje para que "piense" cómo hacerla.
Código
PASO 1 organizar  → script clasifica archivos por reglas fijas
PASO 2 desplegar  → script crea repos + commits reales, sin preguntar
PASO 3 detectar   → script compara hash de hoy vs anterior, versiona solo
PASO 4 subir      → un comando crea remotos y sube todo

ORDEN AL AGENTE (siempre así de corta):
"Ejecuta estos 2 comandos exactos y reporta la salida.
 No analices, no propongas cambios, no decidas nada."

Patrón ya construido y probado (despliegue/organizador.py, desplegador.py, detector_version.py, subir_a_github.sh) — se reusa, no se inventa de nuevo.
